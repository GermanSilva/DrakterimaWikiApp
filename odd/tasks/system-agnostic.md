# System-agnostic campaigns

Let a campaign use any game system, including derived or heavily modified ones, without code changes. Branch: feat/campaign-hub
(follow-up work units). Classification: large and HIGH RISK (item 1/3: the character table, its guard triggers and the stored
campaign data change shape). Status: design agreed, nothing implemented yet.

## Specs

- S1: "Quiero lograr que la página sea realmente agnostica de sistema, para que pueda albergar campañas de cualquier sistema"
- S2: "Me interesa poder albergar rápidamente campañas de otros sistemas, sin ningúno particular en mente."
- S3: "Me interesa tambien poder contener sistemas derivados o intensamente modificados de un sistema original."
- S4 (decision, user): "copia al crear": a template is copied into the campaign when it is created; changing a template later never alters existing campaigns (no inheritance).
- S6 (decision, user): E2 keeps `clase`, `raza` and `nivel` as built-in columns that the profile can disable, rename, and (nivel) give a range; they are not moved into `data`.
- S5 (design): the system is a document (jsonb) stored in the campaign: character fields, currency, vocabulary, active modules. Templates are the same document at hub level ("D&D 5e", "Genérico"); "basado en" is informational only; a campaign can be saved as a new template.

- S7 (user, 2026-10-26, verbatim in Log L5): the sheet structure is built freely by the DM: Categories (tabs of the character editor, not shown in the sheet) > Sections (groups of fields/tables) > display blocks. Fixed Identity category (Visibilidad, Nombre, Jugador, URL de imagen: not deletable). Data types: short text, paragraph, number, boolean; each datum custom or formula (formulas may reference compatible fields); per-field "editable por" (DM only / the character's player). Table types: Stat, Capacidades (linked to a Stat), Habilidad (Nombre, Categoría, free columns), Libre. Block display modes: Stat, Tile, Capacidades, Plano, Modal (Habilidad tables; the block names the categories to filter).
- S8 (consequence): this supersedes the E2 approach of switching D&D blocks on and off and the old E2c (typed custom fields): typed fields become part of the builder. E2a/E2b stay valid for campaigns that keep the legacy D&D sheet.

- S9 (decision, user, 2026-10-27): "No, vamos con la segunda opción": the D&D 5e sheet is REBUILT with the builder (no legacy mode) and the existing character data is MIGRATED to the new structure. Consequence: parity with today's sheet (equipment subtotals and coins, passive perception, spell slots, suggested proficiency bonus, skills grid, attacks, resources, narrative, appearance) is a requirement of the preset, and the migration is a high-risk unit (reversible, dry-run first, own commit, independent verify).

- S10 (design, 2026-10-27): the builder design lives in odd/design/sheet-builder.md (stages F1-F8 replace E2c/E3-sheet parts; E3 currency/vocabulary and E4 templates are folded in). Key idea: keys are identifiers, the D&D preset reuses today's data keys, so existing characters need no data rewrite beyond item id backfill.

- S11 (decision, user, 2026-10-28, verbatim in Log L7): rows of Stat and Capacidades tables are defined by the DM in the sheet template (same rows for every character). The DM chooses whether the player may edit the non-structural values of those rows. Structural parts are editable ONLY from the sheet template, never on a character: Stat = "Nombre" and the modifier formula; Capacidades = "Stat asociado" and the capability name.

- S12 (decision, user, 2026-10-28, verbatim in Log L8): coins are a SPECIAL TABLE that comes built in by default in every template; its rows define the denominations (for example oro/plata/bronce or Galeon/sickle/knut). Until the denominations are defined, lottery prizes cannot be defined and therefore the lottery game does not appear until the configuration is complete.

- S13 (decision, user, 2026-10-28, verbatim in Log L8): the unread dot is per Section.

- S14 (decision, user, 2026-10-28, verbatim in Log L9): denominations have conversion equivalences between them (for example 1 oro = 10 plata = 100 bronce), and the DM defines those equivalences too when configuring the campaign.

- S15 (decision, user, 2026-10-28, verbatim in Log L10): spell slots are a free (Libre) table, one row per spell level (level, total, spent). Libre rows belong to each character, so the DM adds the levels on each sheet; the preset keeps the table editable by the DM only, as today.

- S16 (decisions, user, 2026-10-29, Log L11, summary only): spell slots table [Nivel, Disponibles, Maximo], accidental zero rows not persisted; actions = Modal table Categoria/Nombre/Descripcion plus extra columns per system; "table calculation" element [Titulo, Tabla vinculada, Columna vinculada, Tipo: Suma/Promedio/Conteo/Mayoria/Minoria]; rows sortable by column; flat presentation for now; several economy table instances per sheet; spell extras as extra columns; resettable number columns (A cero / A valor de columna / A valor fijo, icon-only reset button in edit mode) replace Recursos; checkbox default false, numbers 0 unless resettable; hidden formula field; prize encoding helper "20_14_0"; region = built-in field linked to the campaign region catalog.

- S17 (decision, user, Log L12): "Los campos personalizados de la campaña actual se pueden migrar como campos párrafo."
- S18 (decision, user, Log L12): DM notes are a property of section articles and character sheets, not a sheet field.
- S19 (decision, user, Log L12, L13): campaign settings define distance units, their equivalences and the main unit. Text references a distance like an article link, for example `[[{D1}15]]` = 15 of unit 1, rendered with every equivalence as "[15ft|4,5m|3c]" (units "ft", "m", "c"). Conversions round down. Migration keeps legacy distance values as text. Composite text formats are formula fields.
- S20 (decision, user, Log L12, L13): a field can be a checkbox or an option selector; each option has its OWN formula (no shared column formula), example "No competente": {sign}{stat_car:value}+({bonus_proficiencia:value}*0), "Competente" ...*1, "Experto" ...*2 -> "+3", "+5", "+7". The DM is responsible for correct formulas. A formula whose result is a number (no text inserted) offers showing positives with or without a leading "+".
- S21 (decision, user, Log L12): formula fields can be hidden so other fields and functions use them.
- S22 (decision, user, Log L12, L13): the player never edits "gastados"; only the DM does (the F3 rule "a table is player or DM, never mixed" stands). The session panel (DM only) offers buttons on system actions (spell, ability, feat) that update sheet values as configured. An action function is a list of steps; a step that needs a parameter takes it from an earlier step that asks for it (number free or ranged, checkbox, or option list with visible label and hidden value); each step applies its own effect. Exhausted resource: warn and allow forcing. Undo is allowed. Concurrent edit: warn and allow overwriting. Edits made by session buttons do not stamp the unread dot.
- S23 (decision, user, Log L12): system actions are classified (Trucos/Cantrips, spells of each level, class/species features, feats, ...); this replaces legacy `nivel` 10.
- S24 (decision, user, Log L12): hit dice are a formula field returning text.
- S25 (decision, user, Log L12, L13): variants are separate systems. A homebrew system can be branched from the template loaded in a campaign. The hub owner marks systems as "Sistema Origen". A DM requesting a new campaign picks its base among origin systems and the homebrew systems of campaigns under their control. The campaign gets a COPY (S4). The lineage (branched from) is recorded, informational only. An origin system is archived (DMs lose access), never deleted. When a DM stops managing a campaign, a frozen copy of its system configuration is added to their template list; the campaign keeps evolving.
- S26 (decision, user, Log L13): a field removed from a template with characters holding data becomes a "campo descartado": data kept hidden, listed in the configurator so the DM can review each character's data and confirm deletion or restore it to the sheet (moved to the end). Discarded fields are deleted automatically after 60 days.
- S27 (decision, user, Log L13; supersedes S6): fixed identity group always stored as columns (nombre, jugador, imagen, estado, visibilidad, region); everything else (clase, especie, nivel, alineamiento, ...) is a sheet field defined by the system. Level is not universal. Short text and number fields can be marked "Buscables": they become search options and are shown as card tags.
- S28 (decision, user, Log L13): denominations are defined once per sheet; economy instances hold amounts only; exactly one instance can be marked "destino de recompensa" (lottery, pot and rewards credit it); with none, the lottery is hidden.
- S29 (decision, user, Log L13): formulas get LOOKUP (value by key from another table).
- S30 (decision, user, Log L13): a character's player is read-only, set only by the DM when assigning the character to a player (member), never free text.
- S31 (decision, user, Log L13): importing characters of another system is rejected unless forced; a forced import discards the data that does not match.
- S32 (decisions, user approved assistant proposals 1-8, Log L14; refine S19, S22, S25, S26, S27):
  - S19: a distance reference names the unit by KEY, not position: `[[{D:ft}15]]`; the parser reads `[[{D` as a distance and anything else as an article link. Each unit has its own precision (m 1 decimal, squares whole), always rounded down; the decimal separator follows the hub language.
  - S26: restoring a discarded field whose key was reused gets a new key (`magralita_2`) and a warning. The DM is warned in the configurator 7 days before the automatic deletion; exports include discarded fields.
  - S25: the frozen copy holds the template only (structure, formulas, actions), never character data; it is also created when the campaign is deleted.
  - S27: search options and card tags respect field visibility: a field a viewer cannot see is neither shown as a tag nor searchable by that viewer.
  - S22: undo subtracts what the action applied, floored at the field minimum; when the value changed after the action, warn first; the undo history lasts the session.
- S33 (decision, user, Log L14; refines S30): migration discards the legacy free text `jugador` directly (not kept as a discarded field) and fills the system player field with the username of the player assigned to the character.
  - S33 refined (user, Log L16): "username" means profiles.display_name, taken when the character is assigned.
- S34 (decision, user, Log L15): the table calculation element offers Suma, Promedio, Conteo, Mayor, Menor, Mas frecuente and Menos frecuente ("Mayoria/Minoria" of S16 means both the highest/lowest value and the most/least repeated value).
- S35 (decision, user, Log L17): action functions (session buttons of S22) are configured in a SHARED ACTION COLLECTION of the campaign: a catalogue of actions with their function, referenced by the characters (the "later: shared action collection with auto filters" of S16). Open: link vs copy semantics, per-character private actions, per-character state (prepared, uses).
- S36 (decision, user, Log L18; refines S35): a character LINKS collection entries: when the DM corrects an entry it changes for every character; the character stores only its own state per linked entry (for example prepared, uses). A character's own actions also live in the collection, marked private to that character.
- S37 (design, parent, reversible; follows today's permissions): only the DM creates and edits collection entries and their functions; a player sees only the entries linked to their own character (private ones: the DM and that character's owner); per-character state is edited like the other character values (DM, or the player when the sheet opens it). An entry = system category (S23) + name + description + system extra columns + optional function (S22 steps). Storage: a new campaign table with RLS (not inside system_profile: it is campaign content and can grow). The G10 migration turns per-character spell/feature rows into entries (deduplicated by name + category per campaign) plus links.

Finding while scoping E2 (2026-10-26): the character sheet is far more D&D-specific than the three built-in columns: the form has Mecánicas (abilities str/dex/con/int/wis/cha, HP, skills, attacks, spells, resources) and Equipo & Rasgos tabs, the detail page has nine sections (stats, habilidades, ataques, hechizos, recursos, equipo, rasgos, narrativa, apariencia) and the identity tab has "Trasfondo D&D", "Alineamiento" and XP.
